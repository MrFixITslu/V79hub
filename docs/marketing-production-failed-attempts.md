# Clearing failed campaign attempts

The owner requested removing failed campaign packages from the production panel after publication activation. The UI now provides **Clear failed attempts**, an individual **Remove failed attempt** action, and **Show canceled history**. Canceled packages are hidden from the active list by default. Their signed records, events, original assets, idempotency keys and provider receipts remain intact.

Bulk clearing selects only packages whose package status is `blocked` and which have a generation failure message or package review blockers. Every delivery must lack an approval or provider result, and none may be approved, running, succeeded or uncertain. A blocked destination on an otherwise valid pending campaign does not classify the campaign as failed. The existing fresh-MFA owner cancellation API handles each exact job ID sequentially and enforces its worker/started-effect checks. Bulk clearing asks once for confirmation, stops on the first API failure and never automatically retries a mutation. Polling shows partial progress after an interrupted cleanup.

This changes only Hub UI behavior. Marketing code, ledger schema, keys and publication settings are unchanged. Cleanup uses the existing cancellation audit path; it neither deletes packages nor sends content. Previously canceled history can be inspected and hidden again. Actual cleanup occurs only when the owner uses the action in the deployed panel.

Validation: nine component interaction tests including three cleanup regressions, three signed bridge/MFA tests and eight G2 action/ledger tests passed (20 total). The cleanup regressions cover protected delivery states, prior approvals and receipts, pending drafts, disconnected channels, history retention, declining confirmation, expired MFA and partial failures without replay. TypeScript and the production UI build passed. Server image testing and owner acceptance follow the pinned build step; no live deployment was performed during preparation.
